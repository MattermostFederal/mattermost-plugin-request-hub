# Status / SOP working docs

Three short living documents for Security + engineering. Keep them separate on purpose.

| Doc | What it is | What it is not |
| --- | --- | --- |
| [01-sop-before-request-hub.md](./01-sop-before-request-hub.md) | Who owns what **without** Request Hub | Product backlog, UI design, phase lists |
| [02-sop-after-request-hub.md](./02-sop-after-request-hub.md) | Who owns what **with** Request Hub in place | Implementation details or “Planned” engineering notes |
| [03-implementation-progress.md](./03-implementation-progress.md) | What we will build, progress, open questions | Policy language for Security sign-off |

**Why this split:** An SOP answers “who is responsible?” for humans following a process. An implementation progress doc answers “what does the plugin do / will do?” for builders. Mixing them makes SOPs unreadably long and makes progress tracking look like policy.

Local longer draft (bots / ARB / catalog narrative) may still live outside this repo until cleaned up; fold lasting bits into **03** as they stabilize.
