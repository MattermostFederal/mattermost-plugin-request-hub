Docs / Approving

Approving requests

Cards land in plugin-managed private channels under the configured approval team (channel / Channel Admin → mattermost-channel-requests; team creation / Team Admin / team member / guest → mattermost-team-requests; bots → mattermost-bot-requests; webhooks → mattermost-webhook-requests).

Channel and team cards are single-step: one approver decides. Team Admin cards can be approved by System Admins or the Team Admins of the requested team, and go to that team's mattermost-channel-requests channel when it has one. With Team Admins can approve team creation on, Team Admins of the approval team can approve team creation cards. Only a System Admin can approve a request they made themselves. A request an AI agent filed for someone arrives the same way and names that person as the requester; agents can't approve or deny (see AI agents). Bot and webhook cards are two-step (security + system).

Who sees and approves what

Only members of an approval channel see its cards. System Admins on the approval team are added to its channels; per-team mattermost-channel-requests channels hold that team's Team Admins and System Admins; two-step approvers are added to the bot and webhook channels. The requester gets their own copy of the card, without buttons, in a DM thread with the bot.

If a team has no Team Admin or System Admin, its channel cards go to the root channel labeled For Team: …. If there is no approval channel at all (for example, no approval team is set), cards are sent to System Admins by DM.

RequestWho can approve
ChannelSystem Admins and Team Admins of the team the channel will be in; with Team Admins can approve requests on, also Team Admins of the approval team
Channel AdminSystem Admins and Team Admins of the channel's team
Team, Team Admin, team members, guest inviteSystem Admins
Bot, webhookTwo different people: security step, then system step (see below)

Only a System Admin can approve a channel or Channel Admin request they made themselves. Nobody can approve either step of their own bot or webhook request, System Admins included.

Approving from the slash command

Every approval card ends with Request ID: and the request's ID. /mattermost-request-hub list approvals lists the requests you can approve, with their IDs. You can approve or deny a request of any type from any channel with /mattermost-request-hub approve <request ID> or /mattermost-request-hub deny <request ID>. The command makes the same checks as the buttons, in the same order, and replies only to you. See Slash commands.

Once a request is approved, denied or expired, its card is closed with the outcome and the buttons are removed, however the decision was made. When the request went to System Admins by direct message, every copy is closed, not only the one that was clicked. When the first step of a bot or webhook request is approved, every copy shows it. Copies sent before the plugin was upgraded to this version are only closed when they're clicked.

Requests that can't be approved as they stand

A request may have waited a while, so Approve checks it again before acting. If something no longer holds, you'll see a private message ending Deny this request instead., the request stays pending and the card keeps its buttons, so you can deny it. Deny is never blocked, and an expired request closes as expired whatever else has changed.

RequestApprove checks that
ChannelThe team still exists and isn't archived; the requester's account is active and they're still on the team (System Admins excepted); the channel name still matches a configured prefix
Channel AdminThe channel still exists and isn't archived; the requester's account is active and they're still in the channel (System Admins excepted); every nominee's account is active and they're still in the channel
Team AdminThe team still exists and isn't archived; the requester's account is active and they're still on the team (System Admins excepted); every nominee's account is active, isn't a bot or guest, and is still on the team
Team membersThe team still exists, isn't archived and isn't managed by groups; the requester's account is active; every nominee's account is active
Guest inviteThe team still exists and isn't archived; the requester's account is active and they're still on the team and in each channel (System Admins excepted); each channel still exists, isn't archived and is still in the team
TeamThe requester's account is active
BotThe requester's account is active; a chosen owner's account is active and isn't a bot; any webhook channels still exist and aren't archived, the requester is still in them (System Admins excepted), and an outgoing webhook's channel is still public
WebhookThe requester's account is active; the channel still exists and isn't archived; the requester is still in it (System Admins excepted); an outgoing webhook's channel is still public

Bot and webhook requests are checked before either step, so neither step is recorded on a request that can no longer go through. Messages you may see include:

  • The requester's account is no longer active. Deny this request instead.
  • The requester is no longer a member of the team. Deny this request instead.
  • The requester is no longer a member of the channel. Deny this request instead.
  • The team has been archived. Deny this request instead.
  • The team no longer exists. Deny this request instead.
  • ~town has been archived. Deny this request instead. (with the channel's name)
  • @bob is deactivated. Deny this request instead. (with the nominee's name)
  • @bob is no longer a member of the team. Deny this request instead.
  • ~town is no longer in this team. Deny this request instead.
  • Outgoing webhooks need a public channel, and ~town is no longer public. Deny this request instead.
  • The bot owner is no longer an active user. Deny this request instead.
  • The channel name no longer matches the configured prefixes. Deny this request and ask the requester to submit it again.

If something can't be checked at that moment, you'll see Could not check the requester right now. Try again in a moment. or Could not check this request right now. Try again in a moment. instead.

See Troubleshooting if a requester has left.

Expired requests

A request of any type that wasn't reviewed within Request expiry (days) (default 30) can't be approved. Clicking either button on it, or running approve or deny on it, replies This request has expired., marks the card ⌛ Expired: not reviewed within N days., closes the requester's ticket as expired and posts an Expired card to the audit channel. The requester can submit it again.

Bot and webhook requests count from when they were submitted, even after one approval step is done. Only someone who can approve one of their steps can close them as expired.

Bot & webhook two-step approval

Each bot/webhook card needs two distinct approvers on the same card:

  • Security first: security pool (attribute or group). System Admins do not auto-qualify once a security pool is set. Dual-role (both pools / security + System Admin) fills security only.
  • System second: a different System Admin or system-pool member. System-only cannot click before security has signed off.

Configure pools in System Console → Plugins → Mattermost Request Hub → Bot/webhook two-step approver mode.

Mode: User Attributes (ABAC / CPA)

Default. Uses Mattermost User Attributes (custom profile attributes).

  1. System Console → User Management → Attributes: create attributes (admin-managed or LDAP/SAML-synced).
  2. Set Security approver attribute name and System approver attribute name to match your schema (defaults security_approver / system_approver, rename freely).
  3. Mark the right users with those attributes.

System Admins always qualify for the system step. They do not bypass a configured security attribute. Create the attribute and mark security reviewers, or clear the security attribute name if you intentionally want the setup soft-fallback.

Mode: User Groups

Use when ABAC is not available but you have LDAP or plugin-synced groups. Custom groups are not used, because any user can join them.

  1. Create groups (System Console → User Management → Groups). Defaults expect security-approvers and system-approvers. Create those, or rename the plugin fields to match yours.
  2. Set mode to User Groups.
  3. Confirm Security approver user group and System approver user group match the group name/handle (not display name). Both fields are editable in System Console.

Security-group members fill security first. System-group members or System Admins fill system second, always two different people. Someone who is in the security group and a System Admin still only fills security on their click; another person must complete system. If the security group name is blank, System Admins may cover the security step (setup soft-fallback), but a second distinct approver is still required for system.

Mode: System Admins only (no ABAC)

Intentional backup when neither attributes nor groups are set up. Only System Admins can approve; one System Admin can complete both steps on a single click (except on their own request). Prefer attributes or groups in production when you need true two-party separation.
