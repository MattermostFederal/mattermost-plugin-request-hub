Slash commands

Same requests as the hub and native menus, from the message box. Replies are only visible to you.

Requests made with a slash command always go to the approvers, even when a System Admin runs it. An unknown subcommand replies Unknown subcommand `name`. followed by the list above.

/mattermost-request-hub channel

On its own, opens the Request a Channel form. With a prefix and a channel name, it requests the channel in the current team without the form.

Requesting a channel without the form

/mattermost-request-hub channel <prefix> <Channel name> [--suffix <suffix>] [--purpose <text>] [--private] [--members @user ...] [--admins @user ...] [--category <name>]

The prefix comes first, typed exactly as /mattermost-request-hub prefixes lists it (for example team-). Then comes the channel name, which can be several words, then any options in any order. Each option takes the words up to the next --, and each can be given only once.

OptionWhat it does
--suffix <suffix>The URL part after the prefix, as one word. Leave it out to generate it from the channel name.
--purpose <text>A short description of the channel.
--privateMakes the channel private. Without it the channel is public.
--members @user ...Users who become regular members on approval. If you list exactly one member and no --admins, that member is made a Channel Admin, so the channel always has someone who can manage it.
--admins @user ...Users who become Channel Admins on approval.
--category <name>Sidebar category to place the channel in on approval. It can be several words; a missing category is created.

For example:

/mattermost-request-hub channel team- Marketing Team --purpose Campaign planning --members @alice @bob --admins @carol
/mattermost-request-hub channel ops- SRE On-call --suffix sre-oncall --private --category Operations

The request goes through the same checks and approval as the form, and you get the same confirmation.

/mattermost-request-hub channel-admin

On its own, opens the Request Channel Admin form. With @user names, it files the request for the channel you run it in.

Requesting Channel Admin without the form

/mattermost-request-hub channel-admin @user [@user ...]

Run it in the channel itself. You must be a member of it (System Admins excepted), and everyone you name must already be a member too; the request never adds anyone to the channel. The request goes to the System Admins and the Team Admins of the channel's team, the same approvers as the form. The command isn't hidden from people who already admin the channel, but they can manage it directly instead.

ReplyWhat to do
Name at least one channel member...Add at least one @user.
everyone you nominate must already be a member of the channelAdd them to the channel first.
channel not found, or you are not a member of itRun it from a channel you belong to.
Channel Admins can only be requested for public or private channels, that channel is archivedDirect and group messages and archived channels can't have Channel Admins.
you already have a pending Channel Admin request for these people in this channelWait for the existing request to be reviewed.

/mattermost-request-hub prefixes

Lists every prefix your admin configured, with its description and, where there is one, its suffix rule. Use these exactly with /mattermost-request-hub channel.

/mattermost-request-hub list

Lists the requests you made that are still waiting for review, of every type, oldest first. Each line shows what you asked for, the day you submitted it (in UTC), the day it expires if your admin set an expiry, and its request ID. A request that expired before anyone reviewed it is shown as expired (an approver can close it). A request submitted before the plugin started recording submission times shows submitted before the upgrade and doesn't expire. If nothing is waiting, the reply is You have no pending requests.

At most 50 requests are shown, followed by ...and N more when there are others. A type a System Admin turned off isn't listed; with every type turned off the reply is Every request type is currently disabled by an administrator. Approved and denied requests aren't listed: the outcome arrives in your request's direct message thread. Bot and webhook requests also say which approval they're waiting for, security or system.

/mattermost-request-hub list approvals

Lists the pending requests you can approve now, oldest first, in the same format, so you can copy an ID into approve or deny. Your own requests aren't included, nor are types a System Admin turned off. A bot or webhook request is included only when you can fill the step it's waiting for: not when you already approved the other step, and not when only the system step is left and you are a security approver. If there are none, the reply is There are no pending requests you can approve. Finding them reads every pending request, so it can take a moment on a busy server.

/mattermost-request-hub approve

/mattermost-request-hub approve <request ID>

Approves a request of any type without clicking its card. The request ID is at the bottom of every approval card, after Request ID:, in the requester's own copy of the request, and in list approvals. The command makes the same checks as the Approve button, in the same order, and the reply is only visible to you. When it succeeds, the approval card is closed with the outcome, the same as after a click, and the requester's request thread is updated. When the request went to System Admins by direct message (no approval channel), every copy is closed. See Approving for who can approve.

On a bot or webhook request, approve fills your step, as a click would; you don't say which. After the first step the reply is Approved the security step. The request now needs the other approval, from a different person. and every copy of the card shows the approval. The second step, from a different person, creates the bot or webhook.

Like the card buttons, approve and deny still work on a request whose type a System Admin turned off after it was submitted, so pending requests can be closed.

/mattermost-request-hub deny

/mattermost-request-hub deny <request ID>

Denies a request of any type, as its Deny button would. It works the same way as approve.

/mattermost-request-hub exercise

/mattermost-request-hub exercise populate
/mattermost-request-hub exercise status
/mattermost-request-hub exercise teardown

Exercise mode fills a team with believable, clearly marked data for training and demonstrations. Only System Admins can run it, and only while Enable exercise mode is on in System Console → Plugins → Mattermost Request Hub. Run it from a channel in the team you want to seed. Each team has its own exercise data. populate also needs Allow channel requests on and at least one channel prefix, and the setting for every other request type the scenario seeds. The built-in scenario seeds all eight types, and its guest invite also needs guest access on. status and teardown work whatever those settings are, so exercise data can always be removed.

SubcommandWhat it does
populateCreates the scenario's personas, its channels and its pending requests. Each request gets its approval card, in the approval channel the team's real requests use (or as direct messages to System Admins when there is none), and its persona gets the usual request thread. Runs once per team until teardown.
statusCompares what populate recorded with what is still live: active personas, channels not archived, requests still pending, and the teams and bots approvals created. Webhooks are counted but only teardown checks them.
teardownCloses the exercise requests still pending, marking their approval cards and the personas' request threads. Deletes the webhooks and bots that approving exercise requests created, archives the teams and every exercise channel (including any created by an approval), takes Team Admin back from personas and removes personas that were added to the team by a request, deactivates the personas, and removes what the plugin stored about the exercise requests.

Everything exercise mode creates is marked:

  • Personas have the nickname EXERCISE and a position that starts with EXERCISE:. They get a random password that is never shown, so nobody can sign in as one, and email notifications are off.
  • Channel names shown in the sidebar start with EXERCISE, purposes start with [EXERCISE], and each exercise channel's header is an EXERCISE banner.
  • Approval card titles start with EXERCISE, and the message above the card starts with EXERCISE: (after the team label, when the card is routed for another team) and mentions nobody, so populate doesn't notify the approvers.
  • Audit cards and the personas' request threads about exercise requests start with EXERCISE.
  • Teams have a display name that starts with EXERCISE and a URL name that starts with exercise-. Bot usernames start with ex- and their display names with EXERCISE. A webhook request's webhook has a name that starts with EXERCISE, a bot's webhooks are named after the bot, and outgoing webhooks call https://exercise.invalid/hook, which never answers.
  • Guest invites go to exercise-guest-<guest>-<team>@exercise.invalid, a domain that never receives mail.

Seeded requests are made by personas and name only personas, so approving one gives no real user access to anything. Approve and deny work exactly as for a real request, on the card or with approve and deny, and approving does the real thing: it creates the channel, team, bot or webhook, changes the persona's team membership, or sends the guest invite. A bot's token and an incoming webhook's URL go to the requesting persona's request thread, which nobody can sign in to read. Bot and webhook requests still need both approval steps, so in the default user attribute mode they can only be approved once the attribute is set up. Seeded requests don't count toward any real user's pending limit. Channel names use the first configured prefix and must pass its suffix rule.

Teardown only touches what exercise mode created: the requests, channels and persona accounts it recorded, and the teams, bots and webhooks approving its requests created. Real requests, channels, teams, bots and accounts are left alone, even ones that use an exercise name. Teardown waits while a populate is still running in the team.

Nothing is deleted outright

Mattermost doesn't let plugins delete users, channels or teams. Teardown archives exercise channels and teams, renaming each first so the name can be used again, and deactivates the personas. The next populate reactivates the same personas. Bots are the exception: teardown deletes them for good, with their tokens, so their usernames are free again. A guest invite can't be withdrawn; it reaches nobody and expires on its own.

FieldMeaning
id, nameRequired. The name appears in the populate reply.
personasThe people in the scenario, at most 50. role is a short lowercase key that becomes part of the username (exercise-<role>-<team>). off_team keeps a persona out of the team, so a team_member_request can add them. An off-team persona can only be a team member nominee, the requester of a team member or team creation request, or a bot owner.

team_adminFor team_request: the requester also asks to be Team Admin of the new team. suffix becomes the team URL name exercise-<suffix>-<team>, and private makes it invite only.

The outgoing one must be public. suffix becomes the username ex-<suffix>-<team>, which must be 3 to 22 characters.
webhook_typeFor webhook_request: incoming or outgoing. An outgoing webhook needs a public channel.
age_daysOptional, from 0 to 3650. Backdates a request, for example past the expiry so its card shows as expired when approved.

The other request types

On their own, these subcommands open the request form for their type. With arguments, they file the request without it. Team Admin, team member and guest requests are for the team you run the command in. Name channels as ~channel, using the name from the channel's URL, and users as @user. The form, approvers and what happens on approve are described on each type's page.

/mattermost-request-hub team

/mattermost-request-hub team <Team name> [--name <url name>] [--description <text>] [--invite-only] [--team-admin]

The team name can be several words. --name is the URL name; leave it out to generate it from the team name. Without --invite-only the team is open. --team-admin makes you a Team Admin of the new team. See Teams.

/mattermost-request-hub team-admin

/mattermost-request-hub team-admin @user [@user ...]

Asks for those people to be made Team Admins of the current team. You must be a member of the team. See Teams.

/mattermost-request-hub team-member

/mattermost-request-hub team-member @user [@user ...] [--reason <text>]

Asks for those users or bots to be added to the current team. See Team members.

/mattermost-request-hub team-guest

/mattermost-request-hub team-guest <email> --channels ~channel [~channel ...] [--reason <text>]

Asks for a guest invite to those channels of the current team. See Guest invites.

/mattermost-request-hub bot

/mattermost-request-hub bot <username> <Display name> [--description <text>] [--owner @user]

The username is one word; the display name can be several. Access tokens and webhooks for the bot are only in the form. See Bots.

/mattermost-request-hub webhook-incoming

/mattermost-request-hub webhook-incoming ~channel <Display name> [--description <text>]

Requests an incoming webhook that posts to that channel. See Webhooks.

/mattermost-request-hub webhook-outgoing

/mattermost-request-hub webhook-outgoing ~channel <Display name> --callback <url> [--description <text>]

Requests an outgoing webhook for that channel. See Webhooks.

For example:

/mattermost-request-hub team Field Support --description Support for field teams --invite-only
/mattermost-request-hub team-member @alice,@bob --reason Joining the ops rotation
/mattermost-request-hub team-guest guest@example.com --channels ~town-square ~vendor-chat
/mattermost-request-hub bot build-bot Build Bot --description Posts build results --owner @carol
/mattermost-request-hub webhook-outgoing ~deploys Deploy Hook --callback https://ci.example.com/hook

If something is wrong, the reply starts Could not read the request:, says what, and repeats the usage line; nothing is submitted. A name that isn't a user, or a channel that isn't a public channel of the team or a private one you are in, replies unknown user: name or unknown channel: ~name.

Typing arguments

  • Each option takes the words up to the next word that starts with --, so names, purposes and descriptions can be several words.
  • Put quotes around text that should stay as typed, for example --purpose "--draft-- plans". Inside quotes, a word that starts with -- is just text. The quote marks themselves are not saved. Curly quotes work too.
  • Separate users or channels with spaces or commas: @alice @bob, @alice,@bob and @alice, @bob mean the same.
  • A long dash that your device typed in place of -- works like --.

Any request type can also be filed by an AI agent; see AI agents. If a reply isn't clear, see Troubleshooting.
