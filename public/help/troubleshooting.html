Troubleshooting

What a message means, and what to do about it.

"Channel requests aren't configured yet"

/mattermost-request-hub channel, /mattermost-request-hub prefixes and the Agents list_prefixes tool show Channel requests aren't configured yet. Ask a System Admin to define at least one channel prefix in System Console → Plugins → Mattermost Request Hub. A channel request submitted from the form or the Agents request_channel tool is refused with plugin is not configured: an admin must define at least one channel prefix.

Cause: no channel domain prefix is defined. Every channel request needs one. Fix: a System Admin adds at least one prefix under Channel domain prefixes, for example with Load preset.

"... requests are currently disabled by an administrator"

Cause: a System Admin turned that request type off in the plugin settings (for example Allow channel requests or Allow channel admin requests). The type is hidden from the Request Hub and the server refuses it from every entry point. Fix: ask a System Admin to turn it on if you need it.

A request filed before its type was turned off stays pending. Approve on it replies Requests of this type are turned off. Deny this request instead.

Requests arrive as direct messages to System Admins

Cause: the request's approval channel couldn't be used. Rather than drop the request, the plugin sends it by direct message to every active System Admin. This happens for every request type:

  • Channel and Channel Admin requests: the request's team has no per-team approval channel, and Approval team isn't set or can't be found. The server log has the warning no approval channel available.
  • Team, Team Admin, team member, guest, bot and webhook requests: Approval team isn't set or can't be found. When it names a team that can't be found, the server log has cannot ensure named approval channel.

Fix: set Approval team in the plugin settings to the name of an existing team. The plugin creates its approval channels there. Any one System Admin can act on a DMed request; after that, the other copies are closed with the outcome. A copy sent before the plugin was upgraded to this version keeps its buttons, which reply This request has already been handled.

If no System Admin can receive the message either, the requester sees could not send your request to the approvers; try again or contact a System Admin.

"This request has expired"

Cause: the request wasn't reviewed within Request expiry (days). Bot and webhook requests count from submission, even after one approval step. Approve and Deny, on the card or with the slash command, both reply This request has expired., the card is marked ⌛ Expired: not reviewed within N days., and the requester's ticket is closed as expired.

Fix: the requester submits it again. Raising the expiry also applies to requests already pending; 0 turns expiry off. See Expired requests.

"You have N pending requests waiting for review"

Cause: the requester is at Pending requests per user for that kind of request (each request type is counted separately). Expired requests no longer count.

Fix: wait for an approver to act on some, or for them to expire. A System Admin can raise the limit, or set it to 0 for no limit.

A related message starting you already have a pending, such as you already have a pending request for ~name in this team, means the same request is already waiting. It doesn't need to be submitted twice. Each request type's page lists its exact wording.

Approve says someone or something is no longer valid

Approve checks the request again before acting. You'll see a private message, and the request stays pending with its buttons:

  • The requester's account is no longer active. Deny this request instead.
  • The requester is no longer a member of the team. Deny this request instead.
  • The requester is no longer a member of the channel. Deny this request instead.
  • @name is no longer a member of the channel. Deny this request instead. (a nominee)
  • The channel name no longer matches the configured prefixes. Deny this request and ask the requester to submit it again.

Every request type is checked, including its team, channels, nominees and bot owner, and each message tells you to deny the request. The full list is in Requests that can't be approved as they stand.

Fix: deny the request. Deny is never blocked. See Approving.

For a Channel Admin request, Approve refuses if a nominee has left the channel. Only if the nominees leave in the moment after that check does the card say nobody was promoted: the nominees are no longer members, and the requester is told.

Approve says you can't

These replies are private, and the request stays pending for another approver:

  • You can't approve your own request. Another approver has to review it. Only a System Admin can approve their own channel or Channel Admin request.
  • You created this request on a bot or webhook card: nobody can approve either step of their own bot or webhook request, System Admins included. The card shows the reminder for everyone.
  • Security review required first. on a bot or webhook card: a security approver has to approve before a system approver can finish it.
  • You've already approved your step. This request needs a different approver to complete it. The two steps of a bot or webhook card need two different people.
  • You don't have permission to approve or deny this channel request., ... this Channel Admin request. or Only System Admins can approve or deny ... requests. See Who sees and approves what.
  • This button doesn't belong to that request's card. The button was on a post the plugin didn't record for that request. Use the buttons on the request's own card.

/mattermost-request-hub approve gives the same replies for every request type. From the command, the bot and webhook replies start with ⚠️ and give the reason in full, and no card is changed.

Fix: ask an approver who can act on it.

"Try again" messages

Could not check the requester right now. Try again in a moment., Could not check this request right now. Try again in a moment., Couldn't check this card. Try again in a moment., could not load your account; try again and could not save your request; try again mean a lookup or save failed for a moment. This request was just updated. Please click Approve or Deny again., This request was just updated. Please run the command again. and This request was just updated by someone else. Please try again. mean another approver acted at the same moment; the request may already be handled.

Fix: try again. If it keeps happening, check the server log for an error from the plugin.

No cards in the audit channel

Cause: the plugin posts every approve, deny and expiry to the private mattermost-audit-requests channel it creates in the approval team. Without an Approval team, or when the team can't be found, there is no audit channel and nothing is posted. In the second case the server log has cannot ensure named approval channel; when the setting is empty, nothing is logged. If the channel exists but a post fails, the log has audit post failed with the reason.

Fix: set Approval team to an existing team. System Admins are added to the audit channel automatically.

Agents tools not showing

If an agent doesn't offer to file requests, check, in order:

  • Offer tools to Agents is on in the Mattermost Request Hub settings. It's off by default.
  • The Mattermost Agents plugin is installed and enabled, on Mattermost 11.3 or later.
  • The setting for the request type is on; a tool for a type that's off refuses with the disabled message.
  • The tools are allowed in the Agents plugin's settings. They're listed with this plugin's prefix: com_mattermostfederal_mattermost-plugin-request-hub__list_prefixes, com_mattermostfederal_mattermost-plugin-request-hub__request_channel, com_mattermostfederal_mattermost-plugin-request-hub__request_channel_admin, com_mattermostfederal_mattermost-plugin-request-hub__request_team, com_mattermostfederal_mattermost-plugin-request-hub__request_team_admin, com_mattermostfederal_mattermost-plugin-request-hub__request_team_member, com_mattermostfederal_mattermost-plugin-request-hub__request_team_guest, com_mattermostfederal_mattermost-plugin-request-hub__request_bot, com_mattermostfederal_mattermost-plugin-request-hub__request_webhook, com_mattermostfederal_mattermost-plugin-request-hub__list_my_requests, com_mattermostfederal_mattermost-plugin-request-hub__list_requests_to_approve and com_mattermostfederal_mattermost-plugin-request-hub__get_request_status.

See AI agents for what each one does.

Exercise mode

These are replies to /mattermost-request-hub exercise.

"Exercise mode is off": turn on Enable exercise mode in System Console → Plugins → Mattermost Request Hub. Only System Admins can run the command.

"exercise mode seeds channel requests, which are turned off" or "this scenario seeds ... requests, which are turned off": populate files the same requests a user would, so it needs Allow channel requests on, and the setting for every other type the scenario seeds. The built-in scenario seeds all eight types. Nothing was created. status and teardown don't need any of these settings.

"The username @exercise-... is taken by an account that isn't exercise data": a real account has a persona's username. Populate creates nothing in that case. Rename that account, or change the persona's role in the exercise scenario.

"This server or team only allows accounts with email addresses at ...": personas use addresses at exercise.invalid, a domain that never receives mail, and Mattermost only lets accounts from the allowed domains join a team. While you run the exercise, add exercise.invalid to Restrict account creation to specified email domains in the System Console, or to the team's allowed domains, whichever the reply names.

"A team with the URL name exercise-... already exists" or "the username @ex-... is taken": a team or account already has a name the scenario's team or bot request needs. Populate creates nothing in that case. Rename it, or change the scenario's suffix. A team or bot left from an earlier exercise is removed by its teardown.

"This scenario seeds guest invite requests, but guest accounts are off" or "guests can only be invited from ...": approving a guest invite request would fail, so populate refuses first. Turn on Enable Guest Access in System Console → Authentication → Guest Access, and add exercise.invalid to the guest domain list if there is one, or use a scenario without guest invites.

"A channel named ~... already exists in this team": a channel, archived or not, already has a name the scenario needs. Rename it, or change the scenario's suffix.

Status says the exercise is populating when no populate is running: an earlier populate stopped partway. The server log has failed to populate exercise data with the reason. Run /mattermost-request-hub exercise teardown, which removes whatever it created, then populate again. For five minutes after a populate stops, teardown answers a populate is still running in this team, since it can't tell a stopped populate from a slow one. Wait and run it again.

Teardown says some items could not be removed, or status says a teardown started but didn't finish: the record of the exercise is kept, so run teardown again. The server log names each item that failed. A request stored under an exercise request's ID that isn't exercise data is always left alone and reported this way.
